# ICT & Cyber Security Dashboard

A live, single-screen operations dashboard built for a school's IT team, pulling
real-time data from five separate systems into one TV-friendly view: a
ticketing system, network monitoring, a firewall log analyzer, an AI-driven
network detection platform, and a website uptime checker.

This repo is a **de-identified demo build** of a dashboard I built and
maintain in production. No real school, credentials, or infrastructure
details are included, every number you see running this locally is
generated by [`sources/demo-data.js`](sources/demo-data.js). The real
integration code (auth flows, request signing, retry logic) is untouched
and fully readable, it's just never the code path that actually executes
in demo mode. See **[How the demo mode works](#how-the-demo-mode-works)**
below for exactly how that's wired up.

## What it does

- **Tickets** — open ticket counts, priority breakdown, technician workload, pulled from a HaloITSM-style API (OAuth client-credentials flow).
- **Network** — core switch/firewall throughput per campus, VLAN traffic, live firewall session counts, device health, and a 24-hour outage log persisted to disk.
- **Security** — a threat map, blocked URL categories, and firewall alerts pulled from a FortiAnalyzer-style JSON-RPC API (session login, async log search with polling), plus high-confidence breach detections from a Darktrace-style API authenticated with HMAC-SHA1 request signing.
- **Services** — live up/down status for a configurable list of web applications, checked over HTTP with a HEAD-then-GET fallback and per-request timeouts.
- A password-gated login screen with server-side sessions (persisted to disk, not just memory, so a container restart doesn't log everyone out).
- A site-wide alert banner that aggregates the single highest-priority item from every connected system, and only appears when something actually needs attention.

## Tech stack

Node.js, Express, vanilla JavaScript and Chart.js on the frontend (no
framework, no build step), Docker for deployment. No database, all
in-memory with a few small JSON files for the state that genuinely needs
to survive a restart.

## Running it locally

```bash
git clone <this-repo-url>
cd dashboard
cp .env.example .env
docker compose up -d --build
```

Then open `http://localhost:4000` and log in with `demo1234` (or whatever
you set `DASHBOARD_PASSWORD` to in `.env`).

No credentials, API keys, or real systems are needed, `DEMO_MODE=true` in
`.env.example` is all it takes.

## How the demo mode works

Every real integration lives in `sources/` exactly as it would in a real
deployment:

| File | What it demonstrates |
|---|---|
| `sources/halo.js` | OAuth 2.0 client-credentials flow, cursor-based pagination, deriving multiple dashboard metrics from one data pull |
| `sources/observium.js` | REST API integration, deriving device health and an outage log from state-transition detection (not a vendor-provided alert feed) |
| `sources/fortianalyzer.js` | JSON-RPC session auth, async job submission + polling, scoped self-signed-certificate handling (via a dedicated `undici` agent, not a global TLS override) |
| `sources/darktrace.js` | HMAC-SHA1 request signing from scratch, no SDK |
| `sources/servicecheck.js` | Concurrent HTTP health checks with per-request timeouts and a HEAD-then-GET fallback |

None of these are ever actually called when `DEMO_MODE=true`.
[`server.js`](server.js) checks that flag once at startup and, if it's
set, never even `require()`s the real modules, it loads
[`sources/demo-runner.js`](sources/demo-runner.js) instead, which
generates realistic random data on the same refresh intervals the real
sources use, and writes it into the exact same in-memory cache under the
exact same keys. Every API route and the entire frontend are completely
unaware of the difference.

## What this demonstrates

- Integrating with several structurally different real-world APIs (OAuth,
  JSON-RPC with async polling, HMAC-signed REST, plain bearer tokens) in
  one cohesive codebase, each isolated so a problem with one never
  affects the others.
- Real security practices: constant-time password comparison, scoped (not
  global) TLS trust exceptions, HttpOnly session cookies, server-side
  session storage.
- Handling messy real-world API behaviour: a vendor's own `open_only`
  filter that didn't actually exclude every closed ticket, a percentage
  field that silently wasn't what its name implied, a generic timeout
  error that needed unwrapping to find the real cause underneath.
- Docker packaging with a real production concern actually solved: state
  that needs to survive a container rebuild (sessions, config, the
  outage log) is mounted as volumes, not baked into the image, and never
  includes real secrets.

## Project structure

```
server.js              Express app, routes, auth gate
auth.js                Session-based login (constant-time password check)
cache.js                Shared in-memory store every source writes into
sources/
  halo.js               Real integration code (dead path in demo mode)
  observium.js           "
  fortianalyzer.js        "
  darktrace.js             "
  servicecheck.js           "
  demo-data.js          Generates realistic fake data matching every real shape
  demo-runner.js         Populates the cache with demo-data.js instead of real API calls
public/
  index.html            The entire frontend, no build step
  login.html
```

## A note on the live demo

A static, no-backend version of the frontend (same UI, pre-generated
sample data, no login) is deployed via GitHub Pages: **[link here]**.
That version can't run the real Node backend at all (GitHub Pages only
serves static files), so it's a fixed snapshot rather than the live,
self-refreshing version you get running this repo locally.

## Deploying the static demo yourself

The `/docs` folder is a self-contained static build of the frontend,
pointed at fixed sample data instead of a live backend, this is what
GitHub Pages serves. To turn it on for your own fork: **Settings → Pages
→ Deploy from a branch → `main` / `/docs`**. No build step, no Actions
workflow needed.
